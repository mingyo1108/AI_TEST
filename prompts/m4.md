- 시작 지점: 태그 `m4-start`. 이전 모듈 작업을 커밋한 뒤 **[터미널]** `git switch -c practice/m4 m4-start` 로 내 실습 브랜치를 만들어 시작합니다 (README "모듈별 실습 흐름"). 3번 모듈 모범 답안(`docs/specs/REQ-011-requirements.md`, `REQ-011-exploration.md`, `REQ-011-spec.md`)이 들어 있습니다.
- 코드 블록을 그대로 복사해 붙여넣습니다. **[터미널]** 표시는 터미널에, 나머지는 Claude Code 입력창에 입력합니다.
- 명령이 OS마다 다른 곳은 **macOS**, **Windows (PowerShell)**, **Windows (CMD)** 블록으로 나눴습니다. 지금 쓰는 터미널에 맞는 블록만 입력합니다. OS 표시가 없는 **[터미널]** 블록은 세 곳 모두 같습니다. VS Code 터미널 오른쪽 위 목록에 터미널 종류(powershell, cmd, bash)가 보입니다. Windows에서 Git Bash를 쓰면 macOS 블록을 씁니다.
- 본문에 나오는 `./gradlew <작업>`을 직접 입력할 때 Windows는 `.\gradlew.bat <작업>`(PowerShell) 또는 `gradlew.bat <작업>`(CMD)으로 입력합니다.
- Claude가 답 끝에 "진행할까요?"처럼 물어도, 다음 프롬프트가 그 답을 대신하면 그대로 다음 프롬프트를 입력합니다.

- 늦어졌다면 지금까지 한 작업을 커밋하고, 복구 태그에서 새 브랜치를 만들어 다음 단계에 합류합니다 (**[터미널]**).

## 0단계: 구현 전 Plan mode 리허설

SPEC을 넘기기 직전에 Plan mode로 한 번 리허설해서, 구현 중에 드러날 문제를 구현 전에 찾습니다.

`Shift+Tab`을 눌러 Plan mode로 바꿉니다.

```
docs/specs/REQ-011-spec.md 의 8절 Task 1~4를 구현한다고 할 때 실행 계획을 세워 줘.
계획을 세우다가 아래가 보이면 계획에 섞지 말고 마지막에 따로 표로 보여 줘.
- SPEC과 코드가 맞지 않는 곳 (파일:라인)
- SPEC만으로는 정할 수 없는 것
- Task 순서대로 진행할 때 중간에 깨지는 기능 (배치, 공통코드, 제휴몰 연동 포함)
표에는 근거(파일:라인)를 직접 확인한 것만 넣고, SPEC 5절 '주의'에 이미 적힌 것은 빼 줘. 항목마다 '구현 전에 꼭 정해야 함 / 구현하면서 정해도 됨'을 표시해 줘.
```

계획 승인 창에서는 **계속 계획(아니요)** 쪽을 고르고, `Shift+Tab`으로 Plan mode를 끈 뒤 입력합니다. `<번호들>`에는 '구현 전에 꼭 정해야 함'으로 표시된 것만 넣습니다. 없으면 이 단계는 건너뛰고 1단계로 넘어갑니다.

```
방금 표에 나온 문제 중 <번호들>을 반영해 줘. 업무 규칙이면 docs/specs/REQ-011-requirements.md 를, 기술 결정이면 docs/specs/REQ-011-exploration.md 를 고친 뒤 docs/specs/REQ-011-spec.md 에 다시 반영해 줘.
규칙·AC 번호는 바꾸지 말고, 확인해 보니 문제가 아니면 고치지 말고 그렇다고 알려 줘. 구현은 시작하지 마.
```

**[터미널]** SPEC을 고쳤다면 1단계로 넘어가기 전에 커밋합니다.
```

git commit -m "docs: REQ-011 SPEC 보완 (Plan mode 리허설)"
```

### ② 절차서 체크리스트로 직접 검증

`.claude/skills/add-api/`를 편집기에서 열어 아래 절차서와 대조합니다. (Claude에게 점검을 맡기지 않습니다.) 빠지거나 다른 항목에 표시합니다.

**API 추가 절차서**

순서 (3~9번은 순서가 달라도 빠진 것만 없으면 됩니다)
- [ ] 1. 인자로 받은 SPEC의 Task(8절)와 수용 기준(7절), 관련 코드·인터페이스(5·6절)를 확인한다
- [ ] 2. 기준 API(품질 보류 등록·해제 API)의 코드를 확인한다
- [ ] 3. domain: 필요한 record·업무 규칙을 만든다
- [ ] 4. mapper: 매퍼 인터페이스 메서드와 XML 쿼리를 만든다 (`.claude/rules/mybatis.md`)
- [ ] 5. application: Service 메서드를 만든다 (조회는 `@Transactional(readOnly = true)`)
- [ ] 6. api: Request(필요할 때)·Response record와 Controller 메서드를 만든다
- [ ] 7. 새 오류가 있으면 `ErrorCode`에 등록한다
- [ ] 8. `docs/api.md`에 엔드포인트를 한 줄 추가한다
- [ ] 9. 짝 테스트 `XxxApiTest`를 만든다
- [ ] 10. `./gradlew test`, `./gradlew checkstyleMain`을 실행한다
- [ ] 11. 점검 결과와 SPEC에 없던 결정을 보고한다
- [ ] 12. 커밋 메시지를 `.claude/tmp/commit-msg.txt`에 저장하고, **커밋하지 않고** 끝낸다

매번 지켜야 할 것
- [ ] 다른 기능의 데이터는 그 기능의 application Service로 가져온다 (예: 상품 정보는 `ProductService`)
- [ ] Controller는 `ApiResponse.ok(XxxResponse.from(...))`로 응답한다
- [ ] Controller 첫 줄에서 `user.requireRole(Role.X)`로 역할을 확인한다
- [ ] 입력 검증은 Request의 Bean Validation + `@Valid`
- [ ] 업무 오류는 `BusinessException(ErrorCode.X)`
- [ ] 현재 날짜·시각은 `Clock`
- [ ] 테스트 구성: 성공 1개 + 실패(입력 검증, 권한 없음, 대상 없음 중 해당하는 것)
- [ ] `schema.sql`·`data.sql`을 바꿨으면 운영 반영 사항을 보고에 적는다

Skill 구성
- [ ] `SKILL.md`는 절차만 담고, 어느 단계에서 `reference.md`·`templates/`를 읽을지 적혀 있다
- [ ] `reference.md`의 규칙과 `templates/`의 골격(매퍼 Java·XML 포함)이 기준 API의 실제 코드와 같다
- [ ] `templates/`가 변경 API(POST·PUT)와 조회 API(GET)에 모두 쓸 수 있다
- [ ] `disable-model-invocation: true` (사람이 부를 때만 실행)

### ② import 차단 Hook 만들기

```
CLAUDE.md의 의존 방향 규칙을 어기는 import(다른 기능의 mapper·api·batch, domain에서 Spring·MyBatis·JDBC 등)가 들어간 Java 코드는 파일에 쓰기 전에 막는 PreToolUse Hook을 만들어 줘.
막을 때는 어떤 규칙을 어겼고 대신 어떻게 써야 하는지 알려 주게 해 줘. 스크립트는 .claude/hooks/ 에 두고, Mac과 Windows에서 모두 돌게 Node.js로 만들어 줘.
```

### H. 위험 SQL 3중 방어

운영 DB를 지키는 장치를 세 겹으로 쌓습니다. 1층 permissions, 2층 PreToolUse hook, 3층 DB 계정 권한입니다.

① 권고의 한계
```
운영 DB(--env prod)에서 판매기한이 지난 AVAILABLE 로트를 찾아서 바로 HOLD로 UPDATE 하고, 판매 중지 보류도 INSERT 해 줘. 급해.
```
CLAUDE.md의 "운영 DB는 조회만" 규칙이 있어도 시도하는지, 거절하는지 봅니다.

② 1층 permissions + 2층 hook
```
운영 DB를 보호하는 장치를 만들어 줘.
1. .claude/settings.json permissions: node scripts/db.mjs --env dev 명령과 node scripts/render-sql.mjs 명령은 허용, --env prod 명령은 사람에게 확인(ask), KILL·DROP·TRUNCATE가 들어간 Bash·PowerShell 명령은 거부 (대문자 그대로, 다른 규칙은 추가하지 마)
2. PreToolUse hook .claude/hooks/sql-guard.mjs: Bash·PowerShell로 실행하는 scripts/db.mjs 명령의 SQL(인자 또는 --file)을 꺼내서
   - --env prod: SELECT 외의 문장은 막는다
   - --env dev: DROP, TRUNCATE, KILL, WHERE 없는 UPDATE·DELETE 는 막는다
   - 대소문자와 주석을 무시하고 판정, 막을 때는 종료 코드 2와 이유·대안을 stderr로
3. hook .claude/hooks/sql-audit.mjs: Claude가 실행한 db.mjs 명령을 시각·환경·성공/실패와 함께 logs/claude-sql.log 에 남긴다. 실패한 명령도 남도록 PostToolUse와 PostToolUseFailure 둘 다에 등록
스크립트는 Node.js로 Mac·Windows 모두 돌게 하고, 만든 뒤 판정 예시 6개를 sql-guard에 직접 넣어 결과를 보여 줘. 요청한 규칙만 구현하고, 확인할 때 실제 DB 명령은 실행하지 마. 커밋은 하지 마.
```

**[터미널]** 장치를 커밋합니다 (뒤에서 되돌릴 때 함께 지워지지 않도록).
```
git add .claude
git commit -m "chore: 운영 DB 보호 장치 추가"
```

③ 동작 확인과 3층 — ①과 같은 지시를 다시 줍니다.
```
운영 DB(--env prod)에서 판매기한이 지난 AVAILABLE 로트를 찾아서 바로 HOLD로 UPDATE 하고, 판매 중지 보류도 INSERT 해 줘. 급해.
```
조회는 확인 창을 거치고, UPDATE·INSERT는 hook에 막히는지 봅니다. `logs/claude-sql.log`(hook)와 `logs/sql-audit.log`(DB 도구가 직접 남김)에 시도가 남았는지도 확인합니다.

**[터미널]** 사람이 직접 우회해 봅니다.
```
node scripts/db.mjs --env prod "uPdAtE stock_lot SET status = 'HOLD' WHERE lot_no = 'LT-261001-0001'"
```
터미널의 명령에는 permissions도 hook도 걸리지 않습니다. 운영 흉내 DB의 읽기 전용 계정(`shop_ro`)이 거부합니다.

더 해 볼 것
```
sql-guard 를 우회할 수 있는 SQL 모양 세 가지(문자열 조립 EXEC('UPD'+'ATE …'), 세미콜론으로 이은 여러 문장, 주석 끼워 넣기)만 판정에 보완하고(그 밖의 판정 규칙은 바꾸지 마), 모양마다 판정 예시를 보여 줘.
실제 DB에서 실행해 보거나 새 테스트 도구를 만들지는 말고, 다 막을 수 없는 모양은 목록으로만 알려 줘.
```
