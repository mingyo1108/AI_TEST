# 2번 모듈 실습 프롬프트 — 실습 환경 세팅 & 코드베이스 파악

- 시작 지점: 태그 `m2-start`.
- 코드 블록을 그대로 복사해 붙여넣습니다. **[터미널]** 표시는 터미널에, 나머지는 Claude Code 입력창에 입력합니다.
- 명령이 OS마다 다른 곳은 **macOS**, **Windows (PowerShell)**, **Windows (CMD)** 블록으로 나눴습니다. 지금 쓰는 터미널에 맞는 블록만 입력합니다. OS 표시가 없는 **[터미널]** 블록은 세 곳 모두 같습니다. VS Code 터미널 오른쪽 위 목록에 터미널 종류(powershell, cmd, bash)가 보입니다. Windows에서 Git Bash를 쓰면 macOS 블록을 씁니다.
- 본문에 나오는 `./gradlew <작업>`을 직접 입력할 때 Windows는 `.\gradlew.bat <작업>`(PowerShell) 또는 `gradlew.bat <작업>`(CMD)으로 입력합니다.
- Claude가 답 끝에 "진행할까요?"처럼 물어도, 다음 프롬프트가 그 답을 대신하면 그대로 다음 프롬프트를 입력합니다.
- 프롬프트의 경로·API는 이 저장소 기준입니다. 다른 모듈을 보고 싶으면 그 부분만 바꿉니다.

## 1. 실습 환경 세팅

README의 "수업 전 준비"와 "내 GitHub 저장소 연결"을 마친 뒤, 시작 태그에서 실습 브랜치를 만듭니다.

**[터미널]**

**macOS**
```
git switch -c practice/m2 m2-start
./gradlew build
cp .env.example .env
./gradlew dbReset
node scripts/db.mjs --env dev "SELECT COUNT(*) FROM stock_lot WITH (NOLOCK)"
claude
```

**Windows (PowerShell)**
```
git switch -c practice/m2 m2-start
.\gradlew.bat build
Copy-Item .env.example .env
.\gradlew.bat dbReset
node scripts/db.mjs --env dev "SELECT COUNT(*) FROM stock_lot WITH (NOLOCK)"
claude
```

**Windows (CMD)**
```
git switch -c practice/m2 m2-start
gradlew.bat build
copy .env.example .env
gradlew.bat dbReset
node scripts/db.mjs --env dev "SELECT COUNT(*) FROM stock_lot WITH (NOLOCK)"
claude
```

`dbReset`은 개발 DB(`.local/db/dev`)와 운영 흉내 DB(`.local/db/prod`)를 만듭니다. 마지막 명령에서 로트 건수가 나오면 준비가 끝난 것입니다.

## 2. 코드베이스 탐색 체크리스트

15분 동안 탐색합니다. 평소 쓰는 방법이 있으면 그대로 쓰고, 없으면 3절의 프롬프트를 골라 씁니다. 시간이 모자라면 핵심 흐름, 데이터·상태, 함정을 먼저 합니다. 아래 여섯 가지에 답할 수 있으면 충분합니다.

답에 나온 파일:라인은 두세 개를 직접 열어 맞는지 봅니다. 줄 번호는 자주 틀립니다. 답이 너무 길면 "핵심만 15줄로 다시"라고 요청합니다.

| 항목 | 답할 수 있어야 하는 것 |
|---|---|
| 목적과 경계 | 이 시스템(기능)은 무엇을 하고, 무엇을 하지 않는가 |
| 핵심 흐름 | 진입점부터 요청 하나를 끝까지 따라갈 수 있는가 |
| 데이터·상태 | 주요 모델은 무엇이고, 상태는 어디서 바뀌는가 |
| 컨벤션 | 오류 처리, 로깅, 테스트, SQL(사내 MyBatis 컨벤션 `.claude/rules/mybatis.md`)은 어떻게 작성하는가 |
| 함정 | 이름과 다르게 동작하는 곳, 레거시, 숨은 의존성은 어디인가 |
| 수정 시나리오 | "X를 추가하려면 어디를 고치나"에 답할 수 있는가 |

## 3. 탐색 팁

### ① 큰 구조에서 세부 동작으로

체크리스트 순서대로, 넓게 본 뒤 좁혀 갑니다.

목적과 경계
```
이 저장소가 어떤 업무를 맡는 시스템인지 파악하고 싶어.
docs/domain-guide.md 로 업무를 먼저 보고, 그 업무가 실제로 코드에 있는지 진입점(Controller, 배치 Job, 외부 연동)을 찾아 확인해 줘.
5줄 요약과 함께, 기능(product·stock·partner)마다 하는 일 / 하지 않는 일 / 근거(문서 또는 파일:라인)를 표로 정리해 줘. 문서와 코드가 다른 곳은 따로 표시해 줘.
```

CLAUDE.md는 세션을 시작할 때 이미 읽혀 있으므로 따로 읽으라고 하지 않습니다. 문서(업무 설명)와 코드(실제 진입점)를 맞대어 보게 하면, 문서에는 있는데 코드에는 아직 없는 것까지 드러납니다.

구조
```
src/main/java 아래를 기능 → 계층(api·application·domain·mapper·infra·batch) 순으로 트리로 그리고,
매퍼 XML(src/main/resources/mapper)이 어느 매퍼 인터페이스와 짝인지도 표시하고,
기능 사이에 누가 누구를 부르는지 화살표로 표시해 줘.
```

핵심 흐름
```
입고 API(POST /api/lots) 요청 하나를 Controller부터 매퍼 XML의 실제 SQL까지 따라가 줘.
단계마다 파일경로:라인번호(XML 포함)와 하는 일을 한 줄씩 적어 줘.
```

데이터·상태
```
로트 상태(AVAILABLE·HOLD·SOLD_OUT)를 바꾸는 Java 코드와 매퍼 XML의 UPDATE 문을 모두 찾아 표로 정리해 줘.
열: 바뀌는 상태 / 메서드(파일:라인) / SQL(XML 파일:라인) / 조건
```

컨벤션
```
오류 처리, API 응답 형식, 테스트 작성 방식을 실제 코드 예시 하나씩으로 보여 줘.
.claude/rules/ 의 규칙과 다르게 짜인 곳이 있으면 함께 알려 줘.
```

함정
```
이름이나 주석과 다르게 동작하는 곳, 다른 기능이나 데이터에 숨어 있는 의존성을 찾아 줘.
Java에서는 안 보이고 XML·SQL·데이터에만 있는 연결도 찾아 줘.
코드로 확인한 것과 추정을 나눠서 적어 줘. 인용한 파일:라인은 다시 열어 확인한 뒤 적어 줘.
```

수정 시나리오
```
출고할 때 '출고 사유'를 함께 받도록 바꾼다면 어디를 어떤 순서로 고쳐야 하는지 알려 줘. 코드는 고치지 마.
```

실제 데이터 보기 (개발 DB)
```
node scripts/db.mjs --env dev 로 개발 DB의 stock_lot 과 stock_hold 를 조회해서,
보류 중(HOLD)인 로트마다 어떤 사유의 활성 보류가 걸려 있는지 표로 보여 줘.
SQL은 사내 MyBatis 컨벤션(.claude/rules/mybatis.md)대로 써 줘.
```
코드를 읽다가 막히면 실제 데이터를 함께 보게 합니다. DB 접속 정보는 `.env`에 있고 채팅에 입력하지 않습니다.

### ② 출력 스타일 바꾸기

### ③ 그림으로 설명받기: HTML 슬라이드

낯선 모듈 설명 슬라이드
```
src/main/java/com/example/shop/stock 폴더를 읽고, 이 모듈을 처음 보는 개발자를 위한 설명 슬라이드를 만들어 줘.
- 외부 라이브러리 없는 HTML 파일 하나로, docs/onboarding/stock-slides.html 에 저장
- 방향키로 넘기는 10장 이내
- 구성: ① 이 모듈이 푸는 문제 ② 전체 구조도 ③ 핵심 요청 흐름 ④ 주요 파일 3~5개와 역할
  ⑤ 헷갈리기 쉬운 부분 ⑥ 수정할 때 주의할 점 ⑦ 이해도 확인 퀴즈 3문항(지금 코드로 답할 수 있는 것, 정답 위치는 섞어서)
- 코드 인용에는 파일경로:라인번호를 붙이고, 각 슬라이드의 설명 글은 3줄 이내(표·코드 제외)

```

브라우저가 열리지 않는 환경(원격 접속, WSL)이면 파일 탐색기에서 직접 엽니다.

변경 사항을 리뷰어에게 설명하는 슬라이드
```
git log에서 '제휴몰 재고 연동 배치' 커밋을 찾아, 이 변경을 리뷰어에게 5분 안에 설명하는 HTML 슬라이드를 만들어 줘.
왜 바꿨는지 → 무엇이 바뀌었는지(before/after) → 어떻게 검증했는지 → 남은 리스크 순서로.
before/after는 좌우 2단 코드 비교로 보여 줘.
```

개념 학습용 슬라이드
```
이 프로젝트의 판매 보류(사유별 건 단위 보류)가 로트 상태를 바꾸는 방식을 우리 코드 기준으로 설명하는 HTML 슬라이드를 만들어 줘.
일반론이 아니라 실제 호출 경로를 따라가면서, 각 단계에 해당 코드 위치를 표시해 줘.
```

### ④ 그림으로 설명받기: ASCII 다이어그램

전체 구조도
```
이 저장소의 아키텍처를 ASCII 다이어그램으로 그려 줘.
주요 컴포넌트를 박스로, 호출 방향을 화살표로 표시하고 외부 의존성(DB, 배치, 외부 연동)은 구분해 줘.
가로 80자 이내, 박스 안 라벨은 영어로.
```

요청 흐름 (시퀀스 다이어그램)
```
POST /api/lots/{lotNo}/quality-holds 요청이 들어와서 응답이 나갈 때까지의 흐름을 시퀀스 형태 ASCII 다이어그램으로 그려 줘.
각 화살표에 호출하는 메서드명을 적고, 다이어그램 아래에 단계별 파일경로:라인번호를 정리해 줘.
```

상태 전이도
```
StockLot의 status가 바뀌는 모든 경로를 코드에서 찾아서 상태 전이 ASCII 다이어그램으로 그려 줘.
화살표에는 전이를 일으키는 메서드 이름을 적고, 코드상 도달할 수 없는 상태가 있으면 따로 알려 줘.
```

폴더 트리 + 역할
```
src/main/java/com/example/shop 아래를 2단계 깊이까지 트리 형태로 그리고, 각 폴더 옆에 한 줄로 역할을 적어 줘.
```

쓰면서 알아둘 점
- **박스 안 라벨은 영어로 요청합니다.** 한글은 한 글자가 영문 두 칸 너비로 표시되는 경우가 많아 선이 어긋납니다. 설명은 다이어그램 아래에 한국어로 달게 하면 됩니다.
- **파일경로:라인번호를 꼭 요구합니다.** 그림이 실제 코드와 맞는지 바로 확인할 수 있습니다.
- **출력 스타일과 함께 쓰면 좋습니다.** Explanatory를 켜 두면 작업 중에도 왜 그렇게 했는지 설명을 덧붙입니다.
- **문서에 남기려면 저장까지 요청합니다.** 예: "이 다이어그램을 docs/architecture.md에 추가해 줘."

## 4. 이해도 점검: `/goal`

탐색을 마친 세션에서 보냅니다.

```
지금까지 이 세션에서 탐색한 src/main/java/com/example/shop/stock 기준으로 내 이해도를 점검해 줘. 너는 이 코드베이스의 튜터야.

1. 체크리스트 만들기
   이 세션에서 실제로 읽은 코드만 근거로, 내가 알아야 할 항목을 5~6개 만들어 줘.
   분류: 목적과 경계 / 핵심 흐름 / 데이터·상태 / 컨벤션 / 함정 / 수정 시나리오
   각 항목에 근거 파일경로:라인번호를 붙여 줘. 아직 정답은 보여 주지 마.

2. 내가 먼저 설명하기
   항목을 하나씩 제시하면 내가 내 말로 설명할게.
   빠지거나 틀린 부분만 짚어서 보충해 줘.
   내가 "쉽게"라고 하면 비유를 써서 더 쉽게 다시 설명해 줘.

3. 퀴즈
   2단계에서 모든 항목 설명을 마친 뒤, AskUserQuestion으로 항목마다 1문제씩 내 줘.
   단순 암기보다 "이 메서드가 null을 받으면 어떻게 되나", "새 API를 추가하려면 어느 파일부터 고치나"처럼
   흐름 추적이나 수정 위치를 묻는 문제로. 정답 위치는 매번 섞고, 틀리면 다시 설명한 뒤 같은 항목을 다른 문제로 다시 내 줘.

4. 진행표
   매 라운드 끝에 항목 | 상태(미확인/보충함/통과) | 근거 파일 표를 출력해 줘.

5. 마무리
   모두 통과하면 체크리스트, 내가 틀렸던 부분, 핵심 흐름 ASCII 다이어그램을
   docs/onboarding/stock-notes.md에 저장해 줘.
```

이어서 종료 조건을 겁니다.

```
/goal 진행표의 모든 항목이 '통과' 상태이고 notes 파일이 저장될 때까지 세션을 끝내지 않는다. stop after 15 tries
```

이렇게 설계한 이유
- **이 세션에서 읽은 코드만 근거로 삼습니다.** 그렇지 않으면 Claude가 일반론으로 체크리스트를 만들고, 실제 코드와 다른 문제가 나올 수 있습니다.
- **진행표를 매번 출력하게 합니다.** `/goal`은 별도 평가 모델이 대화 기록을 보고 조건 충족 여부를 판단합니다. 표가 대화에 남아 있어야 평가가 정확해집니다.
- **설명을 먼저 하고 퀴즈는 나중에 냅니다.** 객관식만 풀면 찍어서 통과할 수 있습니다. 내 말로 설명하는 단계에서 이해의 빈칸이 먼저 드러납니다.
- **시도 횟수에 상한을 둡니다.** 통과 기준을 못 넘는 항목이 있어도 무한히 돌지 않게 합니다.
- **결과를 파일로 남깁니다.** 다음에 같은 모듈을 볼 때나 다른 팀원 온보딩에 바로 다시 쓸 수 있습니다.

퀴즈를 풀 때 주의할 점
- **퀴즈 창에서 Esc를 누르면 그 자리에서 턴이 끝납니다.** Esc는 사용자 중단이라 `/goal` 평가(Stop hook)가 돌지 않습니다. 사람이 언제든 멈출 수 있게 한 Claude Code의 동작입니다.
- **목표는 지워지지 않습니다.** `/goal`(인자 없이)로 상태를 확인하고, "이어서 퀴즈 내 줘"라고 보내면 다시 이어지며 평가도 그 턴부터 다시 돕니다. 끝내려면 `/goal clear`를 씁니다.
- **모르는 문제는 Esc 대신 직접 입력란에 "모르겠어"라고 답합니다.** 그래야 Claude가 다시 설명하고 같은 항목을 다른 문제로 냅니다.
