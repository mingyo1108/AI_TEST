# 3번 모듈 실습 프롬프트 — 사람의 요구사항을 AI-Ready Spec으로 구조화하기

- 시작 지점: 태그 `m3-start`. 이전 모듈 작업을 커밋한 뒤 **[터미널]** `git switch -c practice/m3 m3-start` 로 내 실습 브랜치를 만들어 시작합니다 (README "모듈별 실습 흐름").
- 코드 블록을 그대로 복사해 붙여넣습니다. **[터미널]** 표시는 터미널에, 나머지는 Claude Code 입력창에 입력합니다. `<꺾쇠>` 부분만 바꿉니다.
- 명령이 OS마다 다른 곳은 **macOS**, **Windows (PowerShell)**, **Windows (CMD)** 블록으로 나눴습니다. 지금 쓰는 터미널에 맞는 블록만 입력합니다. OS 표시가 없는 **[터미널]** 블록은 세 곳 모두 같습니다. VS Code 터미널 오른쪽 위 목록에 터미널 종류(powershell, cmd, bash)가 보입니다. Windows에서 Git Bash를 쓰면 macOS 블록을 씁니다.
- 본문에 나오는 `./gradlew <작업>`을 직접 입력할 때 Windows는 `.\gradlew.bat <작업>`(PowerShell) 또는 `gradlew.bat <작업>`(CMD)으로 입력합니다.
- Claude가 답 끝에 "진행할까요?"처럼 물어도, 다음 프롬프트가 그 답을 대신하면 그대로 다음 프롬프트를 입력합니다.
- 인터뷰 답변지(`m3-answers.md`)는 강사가 따로 나눠 줍니다. 저장소에 두지 않는 이유는 Claude가 탐색하다가 답변지를 읽으면 인터뷰가 의미 없어지기 때문입니다. 고객 회신은 5단계에서 나눠 줍니다.

| 단계 | 하는 일 | 산출물 (`docs/specs/`) |
|---|---|---|

| 2 | 코드베이스 탐색 | `REQ-011-exploration.md` (1~4절) |
| 3 | Claude가 나를 인터뷰 | - |

## 0. Excel MCP 연결

**[터미널]** Claude Code를 실행하기 전에 등록합니다.

**macOS**
```
claude mcp add --scope project excel -- npx --yes @negokaz/excel-mcp-server
```

**Windows (PowerShell)** Windows에서는 `npx`를 `cmd /c`로 감싸야 MCP 서버가 뜹니다. PowerShell이 `--`와 `@`를 다르게 해석하지 않도록 작은따옴표로 감쌌습니다.
```
claude mcp add --scope project excel '--' cmd /c npx --yes '@negokaz/excel-mcp-server'
```

**Windows (CMD)**
```
claude mcp add --scope project excel -- cmd /c npx --yes @negokaz/excel-mcp-server
```

Windows에서 Git Bash를 쓰면 CMD와 같은 명령을 입력합니다.

Claude Code를 실행합니다(프로젝트 MCP 서버 사용 승인 창이 뜨면 승인). 연결을 확인합니다.

## 3. 인터뷰

```
docs/specs/REQ-011-source.md 와 docs/specs/REQ-011-exploration.md 를 바탕으로, 이 기능을 구현하기 전에 정해야 할 것을 AskUserQuestion 도구로 나를 인터뷰해 줘.
- 원문·최종요구사항이나 코드가 이미 답하는 것은 묻지 마 (exploration.md 4절)
- 질문 앞에 [업무] 또는 [기술]을 붙여. [업무]는 고객만 답할 수 있는 것, [기술]은 개발자가 정할 수 있는 것(외부 연동 코드값, API 경로·응답 필드, 저장 방식, 오류 코드처럼 규격과 코드로 정할 수 있는 것)
- 처리를 되돌린 뒤(정정 이후)와 기존 기능과 겹칠 때(다른 보류, 제휴몰 연동, 기존 데이터)는 반드시 따져
- [업무] 질문에 내가 "고객 확인 필요"라고 답하면 미결로 기록하고 다음으로 넘어가
- [기술] 질문은 선택지마다 장단점을 붙이고, 추천안을 맨 앞에 둬
- 구현을 정하는 데 꼭 필요한 것만, 한 번에 2~4개씩 물어. [기술]은 적어도 판매 중지 표현(상태/사유), 처리자·코멘트, API 경로·위치, 오류 코드, 입력 검증을 확인해. 더 물을 게 없으면 미결 업무 질문과 기술 결정을 표 두 개로 요약해 줘
```

인터뷰 중에는 강사가 나눠 준 답변지(`m3-answers.md`)에서 질문 주제에 맞는 답을 골라 붙여넣습니다. 선택지 중에 같은 답이 있으면 선택지를 고르고, 없으면 직접 입력(Other)에 붙여넣습니다.

## 6. SPEC 생성·점검

### ① 생성

```
docs/specs/REQ-011-requirements.md 와 docs/specs/REQ-011-exploration.md 로 docs/templates/spec-template.md 양식에 맞춰 docs/specs/REQ-011-spec.md 를 만들어 줘.
- requirements.md 7절에 미결이 하나라도 있으면 만들지 말고 남은 미결만 알려 줘
- 출처, 결정 이력, 협의 날짜, 템플릿 주석은 넣지 마
- 규칙은 requirements.md 3절(R)과 exploration.md 5절(T)에 있는 것만 써. R·T에 없는 이름·경로·오류 코드가 필요하면 만들지 말고 마지막에 목록으로 알려 줘
- 5절 관련 코드: 수정할 파일은 실제 경로를 확인해서 쓰고, 새로 만들 파일은 아직 없는지 확인한 뒤 경로와 이름을 정해서 써
```

### ② 새 세션에서 점검

SPEC을 만든 세션은 정리본과 인터뷰 내용을 기억하고 있어서, SPEC에 빠진 것을 스스로 채워 읽습니다. 구현할 세션과 같은 조건(SPEC만 아는 상태)에서 점검합니다.

```
/clear
```
```
docs/specs/REQ-011-spec.md 만 기준으로, 이 문서대로 구현을 시작하기 전에 확인이 필요한 점을 모두 뽑아 줘. 코드는 읽어도 되지만 수정하지는 마.
- SPEC만으로 정할 수 없는 것
- SPEC과 실제 코드가 맞지 않는 것 (없는 파일, 이미 있는 파일, 다른 메서드 이름)
- 검증 방법이 없는 수용 기준
```

나온 항목마다 어디를 고칠지 정합니다. **SPEC을 직접 고치지 않고** 원본을 고친 뒤 다시 만듭니다.

구현하는 사람이 SPEC만 보고 멈추거나 잘못 만들 만한 항목을 고릅니다.
```
점검 결과 중 <번호들>을 반영해 줘. 업무 규칙이면 REQ-011-requirements.md 를, 기술 결정이면 REQ-011-exploration.md 를 고친 뒤 REQ-011-spec.md 를 처음부터 다시 만들어 줘(부분 수정하지 마). SPEC 생성 때 알려 준 '없는 이름·경로'도 exploration.md 5절에 먼저 넣어.
고객 확인이 필요한 것은 규칙을 만들지 말고 requirements.md 7절 미결로 넣고, 그럴 때는 SPEC을 다시 만들지 말고 알려 줘.
```

마지막으로 `docs/checklists/spec-checklist.md`로 직접 점검합니다.
